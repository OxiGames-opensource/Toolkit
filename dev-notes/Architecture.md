## Event Bus Rules

OxiToolkit uses an event-driven architecture for communication between runtime, diagnostics, plugins and development tools.

The Event Bus is the only communication layer between independent modules.

### Core Principles

- An event is an immutable data object.
- An event describes a fact that has already happened.
- An event must not contain business logic.
- An event must not modify runtime state.
- An event must not expose mutating operations.
- Each event type has a single owner.
- Listeners must never communicate directly.
- Modules must not bypass the Event Bus.

### Allowed

```text
Runtime -> EventBus -> Diagnostics
Runtime -> EventBus -> Plugin
Runtime -> EventBus -> Tools
Plugin  -> EventBus -> Diagnostics
```

### Forbidden

```text
Listener -> Listener
Plugin   -> Logger
Logger   -> Runtime
Event    -> mutate()
Event    -> execute()
```

### Event Naming

Events describe facts, never commands.

Correct:

```text
ProcessStarted
ProcessExited
ModuleLoaded
HookAttached
DirectDrawCreated
DisplayModeChanged
PluginLoaded
LogWritten
```

Incorrect:

```text
StartProcess
RunLogger
ExecuteHook
DoSomething
AttachHookNow
```

### Event Levels

#### Runtime Events

Generated by runtime components.

Examples:

```text
ProcessStarted
ProcessExited
ModuleLoaded
HookAttached
ApiCalled
```

#### Toolkit Events

Generated by Toolkit infrastructure.

Examples:

```text
PluginLoaded
ListenerRegistered
ConfigurationLoaded
BuildStarted
BuildCompleted
```

#### Diagnostic Events

Generated by diagnostics components.

Examples:

```text
LogWritten
ReportGenerated
StackTraceCaptured
```

### Ownership Rule

Only the owning module may publish its events.

Examples:

```text
Runtime/Process     -> ProcessStarted
Runtime/Hook        -> HookAttached
Plugin/Manager      -> PluginLoaded
Diagnostics/Logger  -> LogWritten
```

Listeners must never re-publish events owned by another module.

### Immutability Rule

Events are created with all required data and never modified afterwards.

Correct:

```text
ProcessStarted(
    pid,
    executablePath,
    commandLine,
    timestamp
)
```

Forbidden:

```text
modify(event)
update(event)
mutate(event)
```

### Listener Rule

A listener may:

- read event data;
- perform its own local work;
- publish new events only if it owns their type.

A listener must not:

- modify the original event;
- call another listener directly;
- invoke another module directly;
- publish events owned by another module.

## Module Facade Rules

Every top-level module exposes a single public interface.

Other modules communicate only through that interface or through the Event Bus.

Internal implementation is private.

### Module Structure

```text
Runtime/
├── Event/
├── EventBus/
├── Hook/
├── Loader/
└── Process/

Diagnostics/
├── Logger/
├── Reporter/
└── StackTrace/

Plugin/
├── Contract/
├── Manager/
└── Registry/

Tools/
├── Builder/
└── Ghidra/
```

### Allowed

```text
Plugin --------> Runtime
Diagnostics ---> Runtime
Tools ---------> Runtime

Runtime -------> EventBus

Runtime -------> Plugin
Runtime -------> Diagnostics
Runtime -------> Tools
```

### Forbidden

```text
Plugin -------> Runtime/Hook
Plugin -------> Runtime/Process
Logger -------> Runtime/Loader
Tools --------> Diagnostics/Logger
Diagnostics --> Plugin/Manager
```

### Module Isolation

Modules own their internal implementation.

External modules must not:

- instantiate internal components;
- access internal services;
- depend on internal directory layout;
- bypass the module facade.

### Single Responsibility

Each module owns one high-level responsibility.

Examples:

- Runtime — execution and lifecycle.
- Diagnostics — logging and diagnostics.
- Plugin — plugin lifecycle.
- Tools — development and research utilities.

Business logic must remain inside its owning module.
